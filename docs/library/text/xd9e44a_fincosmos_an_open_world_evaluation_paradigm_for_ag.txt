Language agents increasingly work for users on the open Web, and finance is where trusting them is hardest.
The data must come from the Web, the strategy lives in the user’s head, and correctness depends on time,
so an agent can fail silently: a strategy the user never asked for, unverified data, or a backtest that uses the
future yields a report as convincing as a correct one. Existing benchmarks close the world somewhere,
fixing the task, the data, or the timeline, and thereby remove these failures instead of measuring them. We
introduce FinCosmos, an open-world evaluation paradigm for agents doing financial work. A simulated
user holds a hidden strategy sampled from a compositional grammar and reveals it only when asked. The
agent receives no data, so it must acquire data from the Web, build its own backtest under a data cutoff, and

1 Introduction
Language agents no longer just answer questions. They work for users in the open world, where the Web is
boththeirsourceofinformationandtheirplaceofwork[8,38,69]. Givenarequest,agentssearchforsources,
call data APIs, write and run code, and hand back results that the user acts on but rarely checks. The question
is no longer whether an agent can solve a task, but whether it can be trusted with one. Finance is where this
question is hardest to answer and where a wrong answer costs the most. The data lives on the Web, not in the
model. Prices, filings, and news are vast, numeric, and change every day, so an agent that relies on memory
hallucinates the figures its results rest on, and even with retrieval, models still miscompute them [5]. The task
intentlivesintheuser’shead. Fewinvestorswantquitethesamestrategy,anditsdetailssurfaceonlywhenthe
agent asks [7, 25, 60]. Correctness lives in the point-in-time. A decision may use only what was public on its
date, yet the Web keeps revising itself, so today’s data carries the future into the past. Each of these produces
a silent failure, in which nothing crashes and the report looks as convincing as a correct one (Figure 1).
Existing benchmarks each close the real world somewhere, and each closure removes a silent failure
instead of measuring it. An agent given curated data, explicit user intent, and an enforced time cutoff never
encounters these failures. As a result, none of them verifies what an agent delivers when the data, the
user’s intent, and the timeline all stay open (Table 1). Closing the intent removes the strategy the user never

2 Related Work
2.1 Financial Agents and Benchmarks
LLM-based agents are increasingly used in finance [18], building on financial LLMs [57]. They range from
trading agents with memory, tools, and multi-agent roles [56, 59, 61, 62, 64] to research agents that mine
alphas, automate factor research, write reports [22, 31, 32, 50], and audit XBRL filings [14, 52]. Each
is evaluated in a setting its designers choose, and look-ahead errors slip in even there [32]. Benchmarks
for these agents have moved from answers to workflows, but they still fix the request when the session
starts. Question-answering benchmarks test reasoning over given reports and filings, across languages and
modalities [6, 19, 39, 57, 58], with results tracked on public leaderboards [33]. Their questions stay fixed
even when they come from real users [13]. Research benchmarks open the data but pose fully specified
questions, graded by accuracy or against expert ground truth [3,70]. Strategy benchmarks hand the agent a
specification and curated data [53, 65], and AlphaOpsBench [21] starts from coarse hypotheses but offers no
user to ask. Agent environments for enterprise decisions likewise pose fixed goals [15]. Trading benchmarks
evaluate decisions in historical or live markets [26, 27, 42], and some enforce point-in-time data inside their
own pipelines [40, 43], so the agent never keeps time on its own. FinTrace [4] evaluates tool calls along the
trajectory, but on predefined tasks. Each opens at most one of intent, data, and time (Table 1).
2.2 Open-World Agent Evaluation
Outside finance, benchmarks open either the intent or the data, rarely both. Simulated users open the intent.
𝜏-bench [60] pairs a tool-using agent with an LLM-simulated user, and its successors add users who act
on a shared environment [2], full-duplex voice [44], and a banking domain with a knowledge base and
discoverable tools [46]. In all of them the user’s intent is hidden, but the world is closed: the agent works over
a fixed database and is graded against a target state [25,41,49]. In finance, benchmarks evaluate advisors
and recommenders over multi-turn dialogue, including against a user’s latent utility [12,51], but they grade
decisions rather than verifiable research deliverables. The fidelity of simulated users is limited: success rates
shift with the simulator model [45], stronger assistants make weaker simulators [37], and no LLM faithfully
reproduces the decisions of individual investors [16]. FinCosmos therefore uses its simulator as an examiner
that discloses a hidden strategy under fixed rules, and validates it with human experts (Section 4.3). Web
benchmarks open the environment instead. Agents are evaluated on sandboxed sites [69], on recorded or
live websites [8], and on open-Web tasks with checkable answers [36,38,54], but the task is stated in full,
even when it is personalized [23]. Deep research benchmarks keep the output open and grade it with LLM
judges [10, 47], which have known biases and can be gamed [35, 66, 67], and flaws in tasks and grading can
shiftagentscoressubstantially[71]. Fixedtasksetsalsogostaleoncemodelstrainonthem,whichLiveBench
counters by refreshing its questions [55] and GDPevo by regenerating tasks [68]. FinCosmos keeps both the
user and the Web open, grades by program-verified invariants wherever possible, and samples new tasks from
a grammar rather than a fixed pool.
2.3 Look-Ahead Bias in Financial Evaluation
Backtests have long been known to overstate performance [1], and LLMs add new routes for leakage. Models
memorize financial values from before their training cutoff [11, 34], LLM trading agents can profit from
leaked outcomes [30], and effective cutoffs can lie months before the dates vendors report [20]. One line
of remedies acts on the model, training it only on data before each date [9, 17] or dampening memorized
outcomes at inference [29]. Another targets the backtest: switching one convention at a time measures how
much each inflates results [63], LLM auditors flag clean backtests as rigged [48], short evaluation windows
overstate LLM strategies [28], and few financial LLM papers discuss these biases at all [24]. These studies
audit models or fixed pipelines. FinCosmos instead checks the data and backtest that each agent builds and

3 FinCosmos
FinCosmos has three components (Figure 2). The Strategy Generator samples a hidden strategy and turns it
into a task (Section 3.2). The User Simulator plays the simulated user, who holds the strategy and reveals it
only when asked (Section 3.3). The Evaluator grades what the agent delivers and returns diagnostic feedback
(Section 3.4). The hidden strategy is sealed: only the User Simulator and the Evaluator can see it, and no
feedback to the agent reveals it.

3.3 User Simulator
The User Simulator is a language model that plays the real user. It separates who the user is (the persona)
from what the user wants (the belief), and a disclosure policy fixes how the belief is revealed.
Persona and belief. The persona pool has three personas: a retail investor, a generalist analyst, and a biotech
specialist (Appendix D). Their prompts forbid evaluation vocabulary, such as “point-in-time” and “cutoff”.
The user states the date up to which data may be used in plain words, but never says that it will be checked.
The belief 𝑏 enters the prompt as plain-language convictions with exact numbers, such as “cut to cash if the
drawdown reaches 20%”, which the user holds and does not read out.

program scores, and edits the memory before the next session. Through these edits, the agent learns from

4.3 Human Evaluation Study
Two financial experts annotate the sessions of the main experiment to check whether the simulator, the LLM
judge, and the evaluator can be trusted. Neither expert took part in building FinCosmos. They complete three
tasks: (1) Simulator fidelity. The experts label every user message as error-free, task-benign, or task-critical
against the hidden strategy. A task-benign error is a slip that does not affect whether a correct agent is
accepted. A task-critical error can prevent a correct agent from being accepted, for example contradicting the
hidden strategy, revealing details that were not asked for, or ending the session against the evidence. (2) Judge
agreement. On a calibration set of 30 of these sessions, the experts grade the four LLM-judged vetoes on the
judge’s anchored 0–4 scale, and we compare their grades with the judge’s. (3) Failure attribution. For every
failed veto, the experts mark whether its reason holds, and for every session, whether the first critical error
came from the agent, the simulator, or the evaluator.
Both experts label every item independently and resolve disagreements by discussion. We report Cohen’s
𝜅 on the calibration grades. Appendix E summarizes the annotation guidelines.
5 Results and Discussions
In this section, 1) We report the main results (Section 5.1), 2) show that the sessions users accept still fail and
that standard grading would count them as successes (Section 5.2), 3) locate where along the workflow agents
break (Section 5.3), 4) test whether the benchmark can be trusted (Section 5.4), 5) and show that agent can
learn from leaderboard’s feedback to solve all tasks (Section 5.5).
5.1 Main Results
Table 3 reports the main results. No agent is accepted in any of the 150 sessions, so pass^𝑘 is 0 for every
agent and every 𝑘. The simulated user was satisfied in 20–33% of the sessions of the four agents, and every
one of these sessions fails at least one veto (Section 5.2). Most sessions end the other way: in 77 of the 120
agent sessions, the user walks away without being satisfied, and 8 sessions reach the turn limit.
Pre-veto quality separates the agents, although ten tasks leave wide intervals. Codex (37.2) and Claude
Code (37.1) are indistinguishable (𝑝= 0.99, paired permutation test over tasks). Codex scores above Gemini
CLI (22.2) and the bare model (20.2), and both differences remain significant after Holm correction (adjusted
𝑝= 0.02); Claude Code’s gap to the bare model does not (adjusted 𝑝= 0.10). Gemini CLI and Kimi Code
(22.3)donotdifferfromthebaremodel,whichhasnotoolsatall(𝑝≥ 0.44). Thebaremodelearnsitsquality
from the strategy (49.8) and user-experience (44.6) categories, which reward a well-described plan, while it
scores 0 on data and 4.6 on the backtest. A fluent conversation is not a correct deliverable.
Quality falls with task difficulty (Spearman 𝜌 =−0.24, 𝑝 = 0.007, over the 120 agent sessions), from
41.6 on tasks of difficulty up to 10 to 26.6 on tasks of difficulty 15 and above. Time is a binding constraint:
70% of agent turns run into the 300-second limit. Cost varies more than quality. Codex reads 3.2 million
input tokens per session, nearly three times as many as Claude Code for the same quality, while Claude Code
is the most expensive at API prices ($2.24 per session, against about $0.80 for the other agents).

deliverable is the basis of a trading decision, they are the costliest failures, and only checks on the delivery
expose them.

Along the workflow. Table 5 follows the sessions through the four steps of the workflow. Agents break most
often at its two ends. Only 25 of the 120 agent sessions deliver the user’s strategy, and none delivers trades

Elicitation. Agents learn little of the hidden strategy. On average, a task’s belief voices 6.7 items, and the

definition for every rule, fails in 68%. Transaction cost, whose options are none or a fixed rate, fails in only

Progress over turns. Per-turn program scores show slow progress: failed program vetoes fall from 5.3 after
the first turn to 3.8 after the sixth. Only 58 of the 120 agent sessions reach a fourth turn; of the 62 that end
earlier, the user walks away in 51.
5.4 Can the Benchmark Be Trusted?
Validity and expert annotation. All 150 sessions are valid. The program validated every simulator decision
before it reached the agent (Appendix D). Grading failed for 2 sittings, which were rerun under the same
conditions. The 60 annotated sessions comprise 13 for each of the four agents, covering all ten tasks, and 8
for the bare model, stratified by end reason within each agent. The calibration set takes three sessions per task
from the four agents and covers the vetoes 2.7, 4.1, 5.1, and 5.6. Agent names are masked, and the experts see
the automatic grades only after tasks (1) and (2) of Section 4.3, when they check failed vetoes and attribute
failures.
Simulator. Both experts flag a task-critical simulator error in the same 3 of the 60 sampled sessions, most
often the user ending the session while the agent was still working. The user walks away in 41 of the sampled
sessions, so at most 3 of these exits are premature: the early endings of Section 5.3 mostly reflect agents that
stall, not an impatient user. The experts attribute 53 of the 60 failed sessions (88%) to the agent, 3 (5%) to the
simulator, and 4 (7%) to the evaluator, so the lack of accepted sessions reflects the agents, not the benchmark.
Judge. On the calibration set, the LLM judge agrees with the experts at 𝜅= 0.87, close to the two experts’
agreement (𝜅 = 0.93). The judge is thus reliable on what it grades; the silent failures it lets through
(Section 5.2) do not show in the conversation or report it reads, and only program checks on the delivery
catch them.
5.5 Learning from Feedback
FinCosmos is built for agents that learn from feedback. A task can be attempted again, and each attempt
returns a diagnostic, leak-free report together with per-turn program scores. Every score records the evaluator
version that produced it, and the leaderboard records every attempt. Together, these provide the infrastructure
for recursive self-improvement: an agent attempts a task, receives its grades, updates itself, and attempts
again, while the hidden strategy stays sealed.
The Claude + Memory agent uses this loop to learn tasks that it could not pass at first (Table 6). No task
is accepted at the first attempt, and the median task fails 8 vetoes in its first session. Through practice, the
agent reaches acceptance on all ten tasks, after a median of 34.5 sessions per task (range 12–132, 506 in total),
and every accepted session passes all 15 vetoes under the current rubric. Practice reduces failures (Figure 3).

by the leak-free rule, so the agent must infer them from the user’s words. Learning from feedback is thus
possible under the leak-free rule, and FinCosmos supplies both the loop and its measurement.
6 Conclusion
Agents doing financial work fail silently: an unrequested strategy, unverified data, or a backtest that uses the
future produces a report as convincing as a correct one. FinCosmos measures these failures by keeping the
user’s intent, the data, and time open, and by grading deliverables against the hidden specification and against
invariants that programs can verify. Our experiments show that no agent completes the workflow. Agents
break most often at its two ends, pinning down the user’s strategy and delivering verifiable results, grading by

user sign-off or by an LLM judge would count their silent failures as successes, and an agent can learn from
FinCosmos feedback.
Limitations. Thebenchmarkfreezestentaskswiththreesessionsperagent,anditsgrammarcoverslong-only
US equity strategies with a fixed-cost model. The simulator, the judge, and one evaluated agent come from
the same model family; program checks and expert annotation limit, but do not remove, this risk. Most agent
turns hit the 300-second limit, so longer turns may let agents get further. Program checks cannot prove that
every figure is real, and feedback scores can leak information about the hidden strategy across attempts, so
leaderboard results should come from frozen agents.
Ethics Statement. FinCosmos uses only public Web data, collects no personal data, and evaluates research
assistance, not investment advice. The two annotators are paid team members doing this as regular work;
judging agent outputs is not human-subjects research.

D User Simulator Details
Personas. Each persona consists of a background prompt, a speaking style, focus areas, example utterances,
and a list of forbidden terms. A retail investor uses finance terms confidently but often imprecisely. A
generalist analyst speaks in a neutral, professional way and asks about metrics such as drawdown, turnover,
and Sharpe ratio. A biotech specialist uses heavy industry jargon and thinks in terms of events such as
catalysts and FDA decisions. The forbidden terms include evaluation vocabulary such as “point-in-time” and
“cutoff”.
Disclosure rules. The simulator’s prompt implements Equation 2 with five rules. (1) Open with a single
vague idea. (2) Answer only what is directly asked. What is not asked, the user cannot recall and does not
volunteer. (3) Asked for a specific value or method, such as a stop-loss threshold, give it directly rather than
asking the agent to propose one. (4) When a proposal conflicts with the belief, object and say what you want.

=== page 23 ===
(5) When a deliverable deviates from the belief, name the piece that is off, such as the position sizing or the
factor source, but do not restate the strategy. The prompt also forbids assistant-like phrases such as “let me
lock a few things”.
Turn decisions. In each turn, the simulator reads the conversation and the agent’s most recent deliverables:
at most 20 files, 8,000 characters per file, and 12,000 characters in total, with the budget going to the newest
files first. Long conversations are compressed to the last six messages and a summary of the earlier ones.
The decision contains an action, one observation per goal of the task, and the next message. The actions are
clarify (answer the agent’s question), follow up (push unfinished work forward), challenge (point out a visible
inconsistency), close, and block, which ends the session without satisfaction and records a reason, such as the
agent giving up or the user walking away. Each observation marks its goal as met, missing, uncertain, or
not applicable and cites the IDs of the supporting messages or files. In the released tasks, the core goal is a
backtest report on the user’s strategy.
Decision validation. A program checks every decision before its message is sent. It rejects a decision that
leaves a goal unobserved, marks a goal as met without citing the agent’s messages or files, closes the session
while a core goal is not met, raises a challenge or a block without evidence, uses internal vocabulary such as
file names of the grading pipeline, asks for more work in a closing message, or repeats an earlier message
verbatim. Arejecteddecisionisregeneratedwiththereasonsforrejection,uptosixtimes. Ifnovaliddecision
results, the simulator run is voided and the session does not count (Appendix C).
